# 2026-07-23

Memory v2 · M1 (truthfulness). The audit that started it: the v1 memory
subsystem is better than it looked — the `memories` table already carries
provenance, confidence, importance, approval status, TTL, and embedding
identity, and `recall.ts` was already hybrid (semantic gate + lexical +
importance + recency). What it could not do was stay TRUE: nothing deduped a
new fact against an existing one, so "launch is in March" and "launch moved to
May" both persisted, both matched, and an agent grounded in memory would state
whichever ranked higher. That is fatal for the delegate (docs/15), so it lands
first.

M1 adds a fact identity and a lifecycle around it: single-valued facts carry a
`factKey` ("project:atlas/launch-date"), and at most one row per
(profile, space, key) may be current. Approving a new value stamps
`validTo` + `supersededBy` on the old one and bumps `revision` — history
survives, recall sees one truth. The supersession filter lives in
`recallRows()` at the repository layer, deliberately, so no caller can ground
an answer in a replaced fact. Migration 0013 is purely additive; the extractor
now emits fact keys and consolidates (identical restatement → re-confirm the
existing row instead of storing a duplicate; contradiction → a pending
candidate the USER approves, never an automatic overwrite). `memory:create`
lets the user author memories directly — still pending, still sensitive-gated,
because authoring is a faster path to review, not a bypass of it.

Testing note worth keeping: the first version of "recall excludes superseded
rows" passed against deliberately broken code. It turned out to be
double-covered — the superseded row was also excluded by its cleared vector,
and then by `validTo` in the past. Only after isolating `supersededBy` as the
single discriminating condition did the mutation actually fail the test. Our
own review rubric calls that class `gaming.test-theater`; mutating the source
to watch the test fail is the cheap way to catch it.

Memory portability (M6), shipped alongside M1 on the same branch. Reasoning
for pulling it forward: memory is about to become the most valuable thing in
the app, and it lived in exactly one SQLite file with no way out — a store the
user cannot get their data out of is not one they should trust with more of
it.

`memory:export` writes a profile's memory as plain, readable JSON to a path
the user picks; `memory:import` merges one back. Plain JSON rather than an
encrypted container is a deliberate trust choice: this is the most sensitive
artefact the app produces, which is exactly why it has to be inspectable —
open it, read it, diff two exports, feed it elsewhere. The app never uploads
it; where the file goes is the user's call. Optional passphrase encryption is
a future addition, not a replacement for legibility.

Import is a merge, never a replace: the sensitive filter runs over every
incoming item (a hand-edited file is untrusted input), duplicates are skipped
by the same normalization the extractor uses so re-importing is a no-op, fact
keys still supersede via M1, an unknown Space name lands profile-global rather
than dangling, and vectors are reused only when the embedding identity
matches. Two modes: `review` (everything pending — for a file from anywhere)
and `restore` (preserves approval — for your own backup, because forcing
re-review of hundreds of items teaches people to rubber-stamp).

Typecheck earned its keep again: the import handler returned
`{imported: true, ...summary}` where the summary's own `imported` is a COUNT —
the spread silently overwrote the boolean. Renamed the flag to `cancelled`.

Memory M2 (recall quality). Started by probing a prerequisite and finding it
absent: **sql.js 1.14 ships FTS3/FTS4 but not FTS5**. An FTS5 virtual table
would therefore fail every migration under the test harness and leave the code
path that decides what an agent says out loud unverifiable — and FTS4 has no
BM25, which was the only reason to want FTS. So the lexical half is IDF-
weighted scoring in JS (`lexical.ts`): testable on every engine, with direct
control over rare-token weighting. Documented in 14-MEMORY §6 so the decision
is not silently re-litigated.

The surfacing contract changed, deliberately. Semantic score was the sole
gate, which meant a memory could never be recalled by NAMING the thing it is
about — embeddings blur identifiers, so "ticket ATL-4471" sits nowhere near
the memory recording ATL-4471. Now either a topical match OR an exact anchor
(the query names something specific the memory contains) can surface it.

Two debugging notes worth keeping. First, `hasExactAnchor` originally
thresholded on raw IDF, which is corpus-size dependent: the same token scores
0.69 among 2 memories and 2.0 among 40, so the anchor silently stopped working
in small stores. Switched to document frequency, which is stable, and the test
now asserts the same token anchors in both a 2-doc and a 40-doc corpus.
Second, two of the first three test failures were fixture artifacts, not bugs:
under fakeVec any two strings with no topic word map to the SAME near-zero
vector, so "unrelated" distractors scored cosine 1.0 against the query. Every
fixture now carries a topic word, which is what makes "the semantic score is
genuinely low" a real condition rather than an accident of the fake.

The benchmark (`recall.bench.test.ts`) replaced two guesses in the doc with
numbers: 1k rows = 24ms, 5k = 65ms, 10k = 137ms. So the 80ms budget is crossed
near 5-6k memories, not the 20k the plan assumed — months away for a profile
fed by daily calls. And lexical now costs MORE than semantic at scale (95ms vs
41ms at 10k) because the index is rebuilt per query, which makes caching the
lexical index the first M5 lever, ahead of any ANN index.

Memory M3 (entities). The structured path similarity search cannot provide:
"what do we know about Acme?" is a join, not a cosine. Two tables (migration
0014) — `entities` (person/org/project/product/place/topic, with aliases and a
merge tombstone) and `memory_entities` — plus a third retrieval path in
recall: when a query names a known entity, every current memory about it joins
the candidate set and gets a ranking bonus.

The design decision that mattered: resolution is EXACT on a normalized match
key or a registered alias, and an unrecognised spelling becomes its own entity
rather than being guessed into an existing one. Over-splitting is visible and
fixed in one click; silently folding two different people called Sarah into
one corrupts memory in a way that is nearly impossible to notice afterwards
and worse to unpick. So merging is a user action, and it is non-destructive —
the loser is tombstoned with a pointer to the winner, so stale references keep
resolving and the loser's spelling starts finding the survivor.

Entity counts and the entity retrieval path both filter to CURRENT memories,
so a fact superseded under M1 never inflates what the app claims to know about
an account.

Verified the entity path by mutation, per the lesson from M2: with
`s.aboutEntity` removed from the surfacing filter, the "recalls memories about
a named entity" test fails — the fixture is phrased so its topic vector points
elsewhere and it shares no query token beyond the name, so neither cosine nor
lexical can reach it. The test measures what it claims to.

Memory M4 (authoring). Four milestones of memory backend had shipped with no
way to reach any of it: `MemoryTab` still only knew list/review/update/archive/
delete, so conflicts, history, entities, and export/import existed and were
invisible. M4 is both the authoring paths the design called for and the surface
that makes M1-M3 and M6 usable.

The refactor that mattered more than the features: consolidation moved into one
shared module (`consolidate.ts`) that every producer goes through. Invariants 1
and 2 — only approved memory is recalled, the sensitive filter runs before
persistence on every path — were previously a rule each new caller had to
remember, and document ingest was about to be the second caller. Now they are
structural.

That refactor also closed a real gap. Deduplication used to happen only for
candidates carrying a `factKey`, so a plain sentence could be re-proposed after
every session forever, and a sentence the user REJECTED came straight back next
time. Matching is now on normalized content within the scope the candidate
would land in — a global memory deduplicates a Space-scoped candidate, another
Space's memory does not.

Document ingest is deliberately less timid than session extraction. A
transcript is something the app overheard, so the <=5 cap and the 0.6 floor are
the price of not being creepy; a document is something the user handed over, so
intent is explicit and it reads the whole thing. Everything else is unchanged.

Found and fixed a bug before shipping it: `chunkText` keeps an over-long
paragraph whole, which is right for the resumes it was written for and wrong
here — extracted PDF text frequently has no blank lines at all and would have
arrived as a single 90,000-character "paragraph", i.e. one enormous model call.
`toWindows` re-splits anything over the window on a sentence boundary. A
document longer than 40 windows is read from the start and the result SAYS so;
a chunk whose model call fails is counted, not swallowed. Reporting "12
proposed" while silently having read half a document is the failure mode worth
engineering against.

Merge and split archive their sources instead of deleting them, so the
judgement stays reversible and readable. Both produce approved rows only when
every input was already approved: the gate exists so nothing the MODEL wrote is
remembered unreviewed, and a human who approved every input and typed the
output has reviewed it. Split does not copy `factKey` onto the parts — several
current rows under one key is exactly what supersession exists to prevent.

Bulk review returns per-item failures rather than throwing. Approving embeds,
so one provider hiccup in a selection of twenty must not silently abandon the
other nineteen.

Six mutants, each caught by exactly its intended test: removing the duplicate
check, copying `factKey` through a split, bypassing `toWindows`, making the
duplicate lookup scope-blind, moving split's sensitive gate inside the write
loop, and dropping bulk review's per-item isolation. 486 tests across 53 files,
typecheck and build clean.
