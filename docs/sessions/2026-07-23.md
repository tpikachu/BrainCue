# 2026-07-23

Memory v2 · M1 (truthfulness). The audit that started it: the v1 memory
subsystem is better than it looked — the `memories` table already carries
provenance, confidence, importance, approval status, TTL, and embedding
identity, and `recall.ts` was already hybrid (semantic gate + lexical +
importance + recency). What it could not do was stay TRUE: nothing deduped a
new fact against an existing one, so "launch is in March" and "launch moved to
May" both persisted, both matched, and an agent grounded in memory would state
whichever ranked higher. That is fatal for the delegate (docs/15), so it lands
first.

M1 adds a fact identity and a lifecycle around it: single-valued facts carry a
`factKey` ("project:atlas/launch-date"), and at most one row per
(profile, space, key) may be current. Approving a new value stamps
`validTo` + `supersededBy` on the old one and bumps `revision` — history
survives, recall sees one truth. The supersession filter lives in
`recallRows()` at the repository layer, deliberately, so no caller can ground
an answer in a replaced fact. Migration 0013 is purely additive; the extractor
now emits fact keys and consolidates (identical restatement → re-confirm the
existing row instead of storing a duplicate; contradiction → a pending
candidate the USER approves, never an automatic overwrite). `memory:create`
lets the user author memories directly — still pending, still sensitive-gated,
because authoring is a faster path to review, not a bypass of it.

Testing note worth keeping: the first version of "recall excludes superseded
rows" passed against deliberately broken code. It turned out to be
double-covered — the superseded row was also excluded by its cleared vector,
and then by `validTo` in the past. Only after isolating `supersededBy` as the
single discriminating condition did the mutation actually fail the test. Our
own review rubric calls that class `gaming.test-theater`; mutating the source
to watch the test fail is the cheap way to catch it.

Memory portability (M6), shipped alongside M1 on the same branch. Reasoning
for pulling it forward: memory is about to become the most valuable thing in
the app, and it lived in exactly one SQLite file with no way out — a store the
user cannot get their data out of is not one they should trust with more of
it.

`memory:export` writes a profile's memory as plain, readable JSON to a path
the user picks; `memory:import` merges one back. Plain JSON rather than an
encrypted container is a deliberate trust choice: this is the most sensitive
artefact the app produces, which is exactly why it has to be inspectable —
open it, read it, diff two exports, feed it elsewhere. The app never uploads
it; where the file goes is the user's call. Optional passphrase encryption is
a future addition, not a replacement for legibility.

Import is a merge, never a replace: the sensitive filter runs over every
incoming item (a hand-edited file is untrusted input), duplicates are skipped
by the same normalization the extractor uses so re-importing is a no-op, fact
keys still supersede via M1, an unknown Space name lands profile-global rather
than dangling, and vectors are reused only when the embedding identity
matches. Two modes: `review` (everything pending — for a file from anywhere)
and `restore` (preserves approval — for your own backup, because forcing
re-review of hundreds of items teaches people to rubber-stamp).

Typecheck earned its keep again: the import handler returned
`{imported: true, ...summary}` where the summary's own `imported` is a COUNT —
the spread silently overwrote the boolean. Renamed the flag to `cancelled`.
