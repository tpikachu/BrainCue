## Local speech-to-text engine (sherpa-onnx + Nemotron)

Filled in the `local` STT contract from yesterday's brainstorm. New doc:
[22 · Local speech-to-text](../22-LOCAL-STT.md).

- `services/stt/modelStore.ts` — `<userData>/models/stt/<id>/`; installed =
  every catalog file at exactly its pinned byte size; `bytesOnDisk` counts
  `.part` remnants; one active download per model, `remove` refuses while
  one runs.
- `services/stt/downloader.ts` — `fetch` to `<name>.part`, Range resume
  (200 → restart, 416 → drop the remnant), 3 retries with back-off, size
  verified before the rename, progress throttled to 250 ms, user-safe errors
  with no paths. Electron-free so it tests against a local `http.createServer`.
- `services/stt/worker.ts` — the recognizer in an Electron `utilityProcess`
  (second rollup input → `out/main/stt-worker.js`). Loads once, reuses the
  recognizer across sessions, per-stream `language` for the multilingual
  model, deltas on text change, finals on sherpa's endpoint rules
  (0.6 s trailing silence after text; 20 s cap).
- `services/stt/localRealtimeStt.ts` — the `local` `RealtimeSttProvider`:
  forks lazily, drops frames until `loaded` (one `reconnecting` status),
  restarts a dead worker once, session ids so a stale final cannot land on
  a newer session. Throws a clear error when the model is not installed.
- `applySttSelection()` registers the provider and selects `local` only when
  the prefs say so AND the model is installed; called at startup (after
  `registerIpc()`), on `settings:set { stt }`, when a download finishes, and
  after a delete.
- `stt.ipc.ts` — the four `stt:*` handlers + `stt:download-progress` push.
- Packaging: `asarUnpack` `**/node_modules/sherpa-onnx-*/**`.
- Dependency: `sherpa-onnx-node@1.13.7` (pulls `sherpa-onnx-win-x64`). The
  addon loads under plain Node 24 on this machine.

## Live test: question detection on both engines (real key, real audio)

`scratchpad/live-test.mjs` boots the BUILT app in isolated E2E mode with the
`.env` key and a junction to the maintainer's downloaded Nemotron EN model,
starts a real meeting session (`session:start`, presence balanced), and
streams two OpenAI-TTS utterances as PCM16 24 kHz at the ScriptProcessor's
pace (8 KB / 170 ms) with silence around them, then records
`transcript:delta` finals, `question:detected`, `contribution:open` and the
streamed answer body.

| | cloud (gpt-4o-transcribe) | local (Nemotron EN, before) | local (after fixes) |
| --- | --- | --- | --- |
| turn 1 final | complete, punctuated | `…start with the road` (cut) | complete |
| question turn | `…campaign?` → heuristic 0.75 | `…campaign` no `?` → classifier 1.0 | no `?` → heuristic 0.72 |
| answer | grounded key points | grounded key points | grounded key points |
| final → answer start | ~0 s | ~4.4 s (classifier round trip) | ~0 s |

Three fixes came out of it:

- **Endpoint rules vs. chunk size** (`stt/worker.ts`): rule2 0.6 s → 1.4 s,
  rule1 1.2 s → 2.4 s. Tokens for a 560 ms chunk only appear once the chunk is
  decoded, so the detector's "trailing silence" includes up to one chunk of
  undecoded speech; at 0.6 s the endpoint fired mid-utterance and `reset`
  discarded the rest of the audio.
- **Warm-up** (`localRealtimeStt.ts` `warmLocalStt`, called from
  `applySttSelection`): the worker forks and loads the model as soon as the
  local engine is selected, not during the first words of the next call.
- **Unpunctuated questions** (`meetingHeuristics.ts`): "Michael What is our
  budget for the third quarter marketing campaign" now reads as a question at
  0.72 (strip a discourse lead and a vocative, then a wh-/aux opener; a wh-word
  followed by a subject pronoun stays a statement). Streaming STT often
  finalizes before the `?` lands; without this the local engine paid a
  classifier round trip on every question.

Test-harness lesson: a real microphone never stops streaming, so the harness
must keep sending silence while waiting — the first version sent two seconds
and stopped, and no endpoint could ever fire under the new rules.

**Re-run after the rebuild + dual capture** (audio tagged `source: 'system'`,
770 tests green, typecheck clean):

| | cloud | local (Nemotron EN) |
| --- | --- | --- |
| turn 1 | `Okay everyone, thanks for joining. Let us start with the roadmap update.` | `Okay, everyone, thanks for joining. Let us start with the roadmap update` |
| question | `Michael, what is our budget …campaign?` → 0.75 | `Michael What is our budget …campaign` → 0.72 (heuristic) |
| final → answer | same tick | same tick |

Both engines detect the question and stream a key-points answer. The dropped
first word seen in the earlier local run was a harness artifact (audio
started at t=0 with no lead-in); with one second of silence first, as any real
microphone provides, the transcript is complete.

**Open observation, not fixed here:** the test profile has no documents, and
both engines' answers still stated concrete budget figures ("$500K",
"$200–250K"). The FABRICATION GUARD in `answer.ts` is worded for interviews
("not in their background … transferable skills") and did not fire for a
meeting question with empty CONTEXT. Worth a meeting-specific guard ("say you
don't have that figure and ask") before the release; noted for the PR review.

## Hear both sides: system audio + microphone, questions from the call

The maintainer's call: "we should listen to both system audio and microphone.
We just care about the questions from system audio, not from the speaker.
Asking the user to select 'listen to' doesn't make sense." So the *Listen to*
choice is gone and a session hears both.

**What changed**

- `shared/activities.ts` — `listensTo` keeps its name with a new meaning, and
  `capturePlan(listensTo)` is the one mapping both processes use: `'system'` →
  streams `[system, mic]`, trigger `system`; `'mic'` → `[mic]`, trigger `mic`.
- Renderer (`store/useLiveSession.ts`) captures both — `getDisplayMedia` for
  the loopback, `getUserMedia` (echo cancellation / noise suppression ON — the
  mic hears the speakers too) for the mic — on one `AudioContext` with one
  `ScriptProcessor` pump per stream, each frame sent as
  `sendRealtimeAudio(sessionId, pcm, source)`. The degrade rules live in the
  pure `lib/captureStreams.ts` (`resolveCapture`): a refused picker → mic
  only + a non-fatal notice via `micError`; a denied mic → call only + notice;
  neither → no session, as before. `speaking` follows the louder stream.
- Engine: `EngineSession.transcribers` holds one `RealtimeSttSession` per
  stream, both opened through `createRealtimeSource`; each tags its turns —
  `system` → `mode.remoteSpeaker`, `mic` → the new `ModeDefinition.localSpeaker`
  (`you` for meeting, `candidate` for interview — the legacy pair Practice
  already writes; companion `you`). `feedRealtimeAudio(sessionId, pcm, source)`
  routes by source and the Cue Card meter shows the louder stream.
  `processFinalTranscript(sessionId, text, speaker?)` defaults to the remote
  speaker, so parity and the meeting acceptance suite pass untouched.
- `onTranscriptFinal(text, speaker)`: every turn is persisted, broadcast and
  remembered; only the remote speaker's turns run the trigger / ambient policy
  / suppressed-answer queue. The user's own turns enter the history tagged
  with their speaker (remote turns keep the v1 item shape — parity pins it),
  and `buildHistoryBlock` renders them as `You said: …` next to `Heard: …`.
- Interim deltas are broadcast for the trigger stream only: the dashboard and
  the Cue Card keep ONE in-flight line, and two streams' partials interleaved
  into it would be unreadable. The mic's words arrive as finals.
- A session started with no activity (rehearsal facades, v1 rows on resume)
  opens the remote transcriber only — v1 behaviour, and what keeps
  `sessionManager.parity.test.ts`'s "one transcriber" assertion honest.
  InterviewPage / TailorPage now pass `activity: 'job'` so real interviews get
  both streams (and their rows record the activity).
- Local engine: `stt/streams.ts` (pure `StreamTable`, `sid → { stream,
  lastText, resampler }`) lets the one loaded recognizer decode several streams
  at once; `audio` messages carry `sid`, `stop` flushes only its sid, `load`
  with sid 0 is a warm-up that opens no stream. `SttWorkerHost` allows N
  concurrent sessions keyed by sid; the restart-once logic reloads and
  re-announces every open session. Cloud engine: two Realtime sockets, so STT
  cost roughly doubles (noted in 06 and 22).
- UI: start modal's radio group → a passive line ("Hears the call (system
  audio) and your microphone. Questions come from the call." / "Hears your
  microphone."); Home chip *Hears: call + mic* / *microphone*; Cue Card
  settings lose the *Listen to* dropdown and always show the mic picker; Help
  FAQ rewritten. `AudioPrefs.source` stays in the type/zod (optional) for old
  settings files; nothing reads or writes it.

**Tests** — new: `engineSession.speakers.test.ts` (a `candidate` turn is
persisted + broadcast + remembered, never triggers; remote default; pending
question queue ignores own turns; teardown stops both), `engine.dualStream.test.ts`
(two transcribers with the right speakers per activity, frame routing by
source, interim for the trigger stream only, meter follows the louder stream,
solo = one mic transcriber tagged `you`, no activity = remote only, stop stops
both), `stt/streams.test.ts` (two sids interleaving deltas/finals on a fake
recognizer), `renderer/lib/captureStreams.test.ts` (degrade rules), an extra
case in `answer.test.ts` (`You said:`); `startFlow.test.ts` updated for the
new capture summary. No existing renderer-store test pattern exists, so
`useLiveSession` itself is covered through `resolveCapture` rather than the
store.

**Not verified live**: the double `getDisplayMedia` + `getUserMedia` prompt

## User test of dual capture: two bugs, both fixed

The user ran a demo call on laptop speakers with the local engine and sent a
screenshot: every remote turn appeared twice (`interviewer: …` then the same
words as `candidate: …`), and the in-flight line read "MorningMorning. Have
you hadMorning. Have you had a chance…".

- **Echo, not a second engine.** Only one STT engine runs; the two labels are
  the two streams, and the microphone was hearing the speakers. Fix:
  `engine/echoGuard.ts` — own turns are held 1.5 s and dropped when the call
  said the same words within 6 s (≥ 80 % word overlap, exact for turns under
  three words; either arrival order); `teardown` flushes held turns; drops are
  logged as a word count. `EngineSession.onTranscriptFinal` now routes own
  turns through the guard and commits via `commitTurn`. Help gains a FAQ
  entry recommending headphones.
- **Local deltas were full-text.** `stt/streams.ts` published the whole
  result on every change, while the cloud engine publishes increments and both
  the dashboard store and the Cue Card append. Now only the added suffix is
  sent (greedy decoding never retracts a token).

Live proof (`ECHO=1 node live-test.mjs local,cloud`: the harness feeds the
same audio to the `mic` stream 170 ms after `system`): both engines transcribe
the mic copy, the guard drops it (two `echo guard: dropped…` lines per
engine), the transcript shows only `them` turns, and the question is still
detected and answered. 783 tests / 82 files, typecheck clean, build OK.

## "Question detection is really slow" — it was the answer path, not detection

User asked whether the cloud transcriber is needed for speed. Measured
instead (harness marks: speech end, final, question, first token):

| | local | cloud |
| --- | --- | --- |
| speaker stops → final | 1.0 s | 1.5 s |
| final → question → open | same tick | same tick |
| open → first token | 3.5 s | 3.2 s |

So detection was instant and the transcriber irrelevant; the 3.5 s was
`ground` 1.5 s (an embedding call for a Space with **no documents**) + first
token 1.75 s, and the first answer of a process paid ~4 s to first token
against 0.9 s for the second (cold connection).

Fixes (see 06 "Answer-path latency"): prefetch grounding on the interim
transcript (`engine.ts` accumulates deltas, `EngineSession.prefetchGrounding`,
consumed by `generateContribution` when the final says the same words);
`retrieve()` skips embedding when `sqliteVectorStore.hasAny()` is false;
`ChatProvider.warm?()` called from `engine.begin` (OpenAI / Anthropic /
compatible). Tests: `engineSession.prefetch.test.ts` (prefetch once per turn,
refresh at +50 %, reuse on matching final, refresh on different final,
statements never prefetch), `retriever.noChunks.test.ts`.

After: ground 0 ms (prefetched), first answer 2.2 s to first token instead of
4.0 s. Controlled TTFT experiment (`scratchpad/ttft.mjs`, real prompt dumped
from `streamAnswer`): 4.1-mini median 1.9 s (chat) / 2.8 s (responses),
4.1-nano 3.0–3.2 s — nano is not faster; a warm `GET /v1/models` is 600–730 ms
from this machine. The remaining ~2 s is vendor + network; options recorded
in 06 (faster provider for the live cue; speculative generation on the
interim). 798 tests / 85 files, typecheck clean.
