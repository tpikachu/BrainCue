# 2026-07-28

Reviewed the whole app against what it has become — an ambient companion for
daily conversations rather than an interview copilot — and found that the docs
made the turn but the code's defaults mostly did not. The engine refactor
genuinely happened; the *defaults* underneath it are still shaped for one person
in one job interview.

The two findings that drove the work:

**Summoning BrainCue in a meeting answers as if it were an interview.**
`meeting.mode.ts` reuses `streamAnswer`, whose system prompt opens "You ARE the
candidate … answering the interview ON THEIR BEHALF … while the interviewer
watches." Correct at the engine level (one generate path), wrong at the prompt
level — the prompt was never generalized alongside the pipeline. Filed as the
next milestone — and fixed in the second pass below.

**Nothing carried across conversations.** `session_reports` were generated and
stored, then read by exactly one screen. `ChunkSource` had no value for a
conversation, so nothing a session produced ever entered retrieval. Every call
began from zero. That is right for an interview — yesterday's interview is not
context for today's — and fatal for a companion in daily calls, where the entire
value is that it was there last time. This is G7 in `14-MEMORY.md`, listed and
left open by M1–M4: memory learned to hold durable facts about the *person*,
which is a different thing from remembering *what happened*.

Built the second one: conversation continuity (`docs/16-CONTINUITY.md`).

At stop, a session is distilled into topic / summary / decisions / action items /
open questions / participants, rendered as one block, and indexed as `session`
chunks so later conversations retrieve it through the path that already exists.

The design question worth recording is why this defaults **ON** when memory
defaults **OFF**. Memory extracts standing assertions about a person and keeps
them indefinitely; getting that wrong means the app states something untrue about
the user, which earns an explicit gate and a review queue. An archive summarises
a session the user deliberately started, from a transcript already on their disk,
and never becomes a claim about them. Requiring opt-in would mean the product's
core promise — it was there last time — is off until discovered. It stays honest
by being visible in Settings, saying exactly what it keeps, running the same
sensitive filter before persistence, honouring the same per-Space opt-out, and
being deleted with its session.

The retrieval cap is the part I expect to matter most in a year. Archives compete
with the corpus for the same top-k slots and they *accumulate*: after a few
hundred calls a profile has more `session` chunks than résumé, notes, and JD
chunks combined, so pure cosine ranking hands the whole context window to
conversation history and the documents that ground factual answers stop
appearing. That failure is gradual and silent — the companion would sound
steadily more confident and steadily less tethered, answering from what was
recently said rather than from what is true. Capped at 2 of 5, over-fetching
first so freed slots go to real alternatives rather than shrinking the result.

Scoping is a confidentiality property, not just a correctness one: an archive
carries its session's `packId`, so a Space-bound call stays inside that Space and
one client's history can never ground another client's meeting. Unscoped sessions
archive globally, which is what makes a personal companion continuous.

Practice drills are never archived — a rehearsal against an AI is not something
that happened, and archiving it would ground future answers in invented
scenarios.

`chunks.source_id` is a plain column, not a foreign key, so SQLite cannot cascade
the deletion; `sessionsRepo.delete` and `deleteAll` remove archives explicitly
and embeddings cascade from `chunks`. An archive outliving its session would keep
grounding answers in a conversation the user deleted.

Four mutants, each caught by exactly its intended test: removing the retrieval
cap, leaving the archive behind on session delete, removing the privacy gate, and
archiving practice drills. 449 tests across 53 files, typecheck and build clean.

## De-interviewing the shared defaults

Second pass, same review: continuity fixed what BrainCue remembered; this fixed
what it assumed. Three shared defaults were still interview-shaped and every
non-interview mode inherited them.

`streamAnswer` now takes an `AnswerFraming`. `interview` is unchanged
byte-for-byte and stays the default, so no existing caller moves; `conversation`
keeps every shared rule (speakable, human, cited, never fabricated) and swaps
the role, with one explicit line: nobody is assessing them here, so never sell,
never perform credentials, never pitch their background unless asked. Meeting
mode asks for it; companion already used the quick-answer generator, which was
never the candidate persona.

The STAR force-include moved behind a mode gate. It is a behavioural-interview
device — right for "tell me about a time you…", wrong for a client call, where
it displaces a real document and invites the model to narrate the user's
achievements. `ground()` takes the mode for exactly this reason.

The mutation run earned its place today. Three mutants, two caught immediately —
removing the story gate, and unconditionally emitting the interview scaffolding.
The third, flipping meeting mode's framing back to `interview`, broke NOTHING.
The rendering tests proved both framings render correctly; nothing proved the
mode was wired to the right one, which is precisely the bug that shipped in the
first place. Added `meeting.framing.test.ts`, which drives `meetingMode.generate`
through a scripted provider and asserts on the actual system prompt. It fails
under the mutant now.

One test fixture also had to be rewritten rather than trusted: the first
story-gate test passed under the gate and failed to distinguish anything,
because the story chunk was winning the top-k on cosine — it appeared under
every mode and always would have. A story that ranks in normally is just a
chunk; only force-inclusion is gated. The fixture now scores the story at ~0.71
against the query, above the 0.3 cue threshold and below six notes at 1.0 that
fill all five slots, so it can appear ONLY via the force path.

The parity suite caught the retrieve() signature change and now pins
`storyCue: true` for interview mode — worth keeping, since it stops the
interview path silently losing its "Story to tell" cue later.

Job-search tooling (Tailor, applications, STAR story bank) is quarantined behind
`FLAGS.jobSearch`, not deleted. Tables, IPC, repositories, and pages are intact;
user data is untouched; one flag restores the surface. It belongs to the
interview-copilot product and Home leading with résumé tailoring misrepresents
what BrainCue is — but deleting shipped features from a released version needs a
deprecation path, not a delete key, and the roadmap's own rule is that interview
mode never regresses in the name of generality.

Home now orders modes by what the product is: Meeting and Companion first,
Interview and Practice after them, still fully shipped. Fixed the product
description in package.json and CLAUDE.md, and retired the last use of the
deprecated `schema.jobs` alias.

458 tests across 54 files, typecheck and build clean.
